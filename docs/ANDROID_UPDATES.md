# Обновления Android и постоянная подпись

## Как это работает

В приветственном меню и меню партии есть «Проверить обновления». По нажатию приложение обращается к публичному GitHub API этого репозитория. Фоновых обязательных запросов, учётной записи GitHub, токена в APK и загрузки удалённых скриптов нет; без сети игра работает.

Клиент принимает только опубликованные стабильные Releases с тегом `android-N` и строго ожидаемым APK этого тега: с 0.14 предпочтительно `Bunker-Posledniy-Shlyuz-N.apk`, либо совместимым `bunker-N.apk`. Старые и равные версии не предлагаются, черновики, prerelease, неправильные имена и посторонние URL отклоняются. Нет релиза — сообщается, что подписанные обновления пока не опубликованы. Ошибки сети и ограничения API не блокируют игру.

Кнопка скачивания открывает официальный APK в системном браузере. После скачивания пользователь открывает файл и подтверждает установку в Android. Возможно, понадобится разрешить установку приложений из используемого браузера. Это **не тихая установка**: APK не скачивается внутри Godot и системный установщик не запускается нативным плагином. Кнопка проверки запускается вручную, автоматических уведомлений при старте пока нет.

Подлинность APK и возможность обновления установленного пакета проверяет Android по сертификату подписи. Отдельной клиентской проверки SHA-256 скачанного файла нет: загрузку ведёт браузер. SHA256SUMS публикуется рядом с APK для ручной проверки.

## Первая установка

Старые тестовые сборки до подключения постоянных Secrets подписывались временными ключами разных CI runner. Перейти с такой сборки на постоянно подписанный Release поверх неё, как правило, нельзя: Android отклонит несовпадение подписи. Один раз потребуется удалить старую установку и установить APK из первого подписанного Release. Это удалит локальный профиль; существующая партия и так не сохраняется между запусками.

После этого для обычных обновлений приложение **удалять не нужно**. При неизменном package ID `org.bunker.prototype`, прежнем ключе и увеличенном version code Android устанавливает обновление с сохранением данных. Не используйте старые preview APK для первоначального перехода на постоянную подпись.

## Где хранятся ключи

Три Repository secrets в GitHub Actions:

- `BUNKER_KEYSTORE_BASE64` — содержимое PKCS#12 в Base64;
- `BUNKER_KEYSTORE_PASSWORD` — пароль контейнера и ключа;
- `BUNKER_KEY_ALIAS` — alias записи.

Значения не коммитятся и не публикуются в Releases. На runner ключ декодируется в приватный файл с правами 0600; release-параметры Godot передаются через поддерживаемые переменные окружения. В APK приватного ключа и пароля нет. После job временные файлы удаляются. Public release pipeline не имеет fallback на случайную подпись.

Сохраните исходный ключ и пароль в защищённом резервном хранилище. Утрата ключа лишит возможности подписывать следующие обычные обновления тем же сертификатом. Не генерируйте новый ключ для каждой версии. Доступ на запись к репозиторию и workflow должен быть только у доверенных людей: такой доступ потенциально позволяет использовать его signing secrets в CI.

`tools/create_signing_bundle.py` предназначен только для локальной первоначальной генерации, требует Python cryptography и отказывается перезаписывать имеющийся архив. Он не запускается в публичном CI. Приватный архив передан владельцу отдельно, в Git и снимки исходников `.cache` не входит.

## Выпуск следующей версии

1. Изменить приложение, увеличить **оба** значения: `version/code` в `export_presets.cfg` и `VERSION_CODE` в `game/scripts/app_updates.gd`. Обновить также обе строки версии. Тест проверяет их совпадение.
2. Перед публикацией выставить `data/release-request.json` → `version_code` равным новому коду. Несовпадение запроса блокирует автоматическую публикацию даже при настроенных Secrets, что позволяет сначала проверить рендеры. Пуш изменений приложения в рабочую ветку запускает `Publish signed Android update`. При отсутствии полного набора Secrets автоматическая публикация пропускается; принудительный ручной запуск без них завершается ошибкой.
3. Workflow выполняет все `tools/test_*.gd`, экспортирует release APK, проверяет его через `apksigner verify` и сверяет package ID/version code с помощью `aapt`.
4. Перед публикацией скачивается предыдущий подписанный APK и сверяется сертификат через apksigner. Изменение сертификата блокирует выпуск. Основной APK имеет фирменное имя; идентичная legacy-копия сохраняется для обновления клиентов 0.13. Создаётся draft Release с APK и SHA256SUMS. Только после загрузки файлов он публикуется как latest. Существующий тег версии не перезаписывается: для новых файлов нужен новый version code.
5. Установленная предыдущая подписанная версия увидит новый Release через кнопку проверки.

Workflow также поддерживает `workflow_dispatch`. Для появления новой workflow в интерфейсе ручного запуска GitHub может потребоваться её присутствие в default branch; поэтому первичный запуск в текущей рабочей ветке выполняется пушем. Если Secrets добавлены после последнего запуска, можно обновить `data/release-request.json` и запушить этот запрос. При уже опубликованной версии повторная публикация заблокирована.

Обычный debug workflow использует постоянный ключ, если Secrets заданы. Без них он остаётся только временным preview с явным предупреждением и не публикуется как обновление.

## Что проверено автоматически

Тесты разбора metadata: новая/равная/старая версия, URL из другого источника, некорректный тег, неверная схема, draft/prerelease. Реальный диалог создаётся и закрывается без сетевого запроса, скачивание по умолчанию заблокировано. Release job проверяет итоговый APK инструментами Android SDK.

На физическом устройстве ещё нужно проверить разрешение установки из браузера, скачивание и переход между двумя последовательно выпущенными подписанными версиями. Наличие кода обновления и успешная проверка подписи не заменяют такой тест.
